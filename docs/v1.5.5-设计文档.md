## 第一部分 · 产品设计

## 一、产品概述

PonyoWallpaper 是一个常驻托盘的 Windows 桌面壁纸应用。它做三件事：

| 能力 | 说明 |
| --- | --- |
| **找图** | 从多个壁纸站点聚合图片，瀑布流浏览，无限下拉 |
| **用图** | 一键设为桌面壁纸（支持多显示器）、收藏、加入自动轮换池 |
| **换图** | 按设定间隔自动轮换，支持快捷键 Ctrl+Alt+N / Ctrl+Alt+P 手动切换 |

设计立场上有三个明确的取舍，贯穿全部版本：

1. **只要电脑横屏壁纸** —— 竖屏/手机壁纸一律不接入，不做尺寸自适应裁切（用户明确要求）。
2. **零解码依赖** —— 只处理 JPEG / PNG，不引入 webp/avif 解码库（本机 WIC 无 webp codec，见 §14）。代价是放弃若干只提供 webp 的素材站。
3. **开箱即用** —— 默认启用的三个源全部免注册、免代理；需要配置能力的源（wallhaven）保留但不默认勾选。

### 1.1 当前版本解决的问题

v1.5.5 是一轮**以用户反馈驱动的修复版本**，五条反馈对应五项改动：

| # | 用户反馈 | 改动 |
| --- | --- | --- |
| ① | 「筛选单个源还会混入其他源」 | 新增 `BrowseSource` 单选锁定，源菜单顶层互斥单选，硬保证只取该源 |
| ② | 「不同源应该展示不同分类」 | 左侧树随浏览源变化，单源时显示**该源自己的分类** |
| ③ | 「多选时只显示几个大类」 | 多源混排时树只显示 4 个大类（风景/摄影/人物/动漫） |
| ④ | 「默认反代怎么都无法访问」 | 定位到 3 个真实缺陷并修复（并发链路横跳 / 单源超时过紧 / 测速探针打直连） |
| ⑤ | 「首页切换、点图 CPU 飙升」 | 三处热点优化（两段缩放 / 批量重排 / 预览窗预缩） |

## 二、壁纸源能力矩阵

应用内注册 4 个源，各自定位不同。**默认启用**（`SourceRegistry.DefaultEnabled`）= 360 + WallpaperCave + GitHub。

| 源 | 显示名 | 默认 | 需要代理 | 分类体系 | 图片管线 |
| --- | --- | --- | :---: | --- | --- |
| `qh360` | 360 壁纸 | ✅ | ❌ 免注册国内源 | **自家 18 类**（风景大片/小清新/萌宠动物/…） | 原图或 1600×900 变体（按分辨率档位切换） |
| `wallpapercave` | WallpaperCave | ✅ | ❌ 免注册国际源 | **检索词**（landscape / city / anime girl …） | `/wp/wpNNN.jpg` 原图 + `/wpt1x/` 小图 |
| `github` | GitHub 图库 | ✅ | ⚠ 需多链路 | **仓库目录关键词**（landscape / anime / minimal …） | 5 个开源仓库，≤1MB 的 jpg/png |
| `wallhaven` | Wallhaven | ❌ | ✅ 需反代/代理 | **23 通用频道**（本应用的频道体系本体） | 需 API，分辨率/分级/排序控制最全 |

### 2.1 各源定位说明

**360 壁纸（`qh360`）** —— 唯一纯国内源。接口是 HTTP（该站不支持 HTTPS），返回 18 个分类。数量大、更新快，但**分类粒度粗**：只有「风景大片 / 小清新 / 萌宠动物 / 炫酷时尚 / 动漫卡通 / 4K 专区」等大众向分类，没有「城市建筑」「星空宇宙」这种细分。

**WallpaperCave** —— 国际源，国内可直连。它是**专辑制**站点：搜索页列出专辑，专辑页服务端渲染出全部图片，每张带 `width`/`height` 属性 —— 这让「只要横屏」的过滤可以在解析阶段精确完成。实测该站搜索对**单词**召回最好（每词 20~47 个专辑），双词组合大量返回 0，所以逐频道只指定一个关键词。

**GitHub 图库** —— 把 5 个开源壁纸仓库当图库用（约 4700 张）。取图走公共镜像多链路，不需要任何配置。分类靠仓库**目录名**匹配。其中一个仓库（D3Ext/aesthetic-wallpapers，380 张）是 MIT 许可。

**wallhaven** —— 功能最全（23 频道 + tag 语法 + 分级 + 排序），但国内直连不可达，必须走反代/代理。保留在菜单中由用户按需勾选，同时也承载 NSFW 分类（需 API Key）。

### 2.2 明确排除的站点

以下站点在 v1.5.0 / v1.5.1 期间实测过，结论是**不可用**，不再重复探测：

| 站点 | 结论 | 原因 |
| --- | --- | --- |
| 哲风壁纸 haowallpaper.com | ✗ | API 全 404（JS 挑战）；原图接口返回 401 |
| 故宫 dpm.org.cn | ✗ | 纯客户端渲染，无可用接口 |
| 壁纸湖 bizihu.com | ✗ | 抽样 12 张全部竖屏（手机壁纸） |
| phwalls.com | ✗ | 连接被重置 |
| Wallhalla | ✗ | 接口可用但变体图只有 webp/avif（与零解码依赖冲突） |
| 已删除的 Bing/Unsplash/Pexels/Pixabay/Picsum | — | v1.5.0 依用户要求移除（保留不提供电脑横屏壁纸或需 Key 的源） |

## 三、交互设计

### 3.1 源菜单：两个正交概念

这是 v1.5.5 最重要的交互改动。菜单拆成上下两段：

```
┌─ 壁纸源 ─────────────────────────┐
│ ◉ 全部（多源混排）                │  ← 浏览源（单选，互斥）
│ ○ 360 壁纸                        │     决定「左侧树显示什么分类」
│ ○ WallpaperCave                   │     决定「图从哪个源来」
│ ○ GitHub 图库                     │
│ ○ Wallhaven                       │
├──────────────────────────────────┤
│   以下勾选项在「全部」模式下参与取图  │  ← 说明行（灰字，不可点）
│ ☑ 360 壁纸                        │  ← 参与源（多选）
│ ☑ WallpaperCave                   │     只在上段选「全部」时生效
│ ☑ GitHub 图库                     │
│ ☐ Wallhaven                       │
└──────────────────────────────────┘
```

| 概念 | 配置字段 | 类型 | 作用 |
| --- | --- | --- | --- |
| **浏览源** | `AppConfig.BrowseSource` | 单选（空 = 全部） | 只看哪个源；决定左侧分类树形态 |
| **参与源** | `AppConfig.EnabledSources` | 多选列表 | 「全部」模式下哪些源参与混排取图 |

**为什么这么改**：旧版把「只看此源」放在每个源的**二级子菜单**里，父项带展开箭头 —— 用户点父项文字时实际触发的是勾选切换，「筛选单个源」的意图经常落空。更糟的是旧代码在结果为空时会**兜底把默认源加回来**，导致「明明只选了一个源，却混进其他源的图」。现在：

- 浏览源提到顶层、互斥单选，**不允许被取消**（点当前项无效果）；
- `SourceRegistry.Enabled()` 里**不再有任何兜底加回**（§7.1）；
- 按钮文字随状态变化：锁定时显示 `壁纸源 360 壁纸`，混排时显示 `壁纸源 3`。

### 3.2 分类树：随浏览源切换形态

左侧树的内容由 `BrowseSource` 决定（`MainForm.BuildTree()`）：

| 浏览源状态 | 树内容 | 节点 Tag |
| --- | --- | --- |
| 全部（多源混排） | **只显示 4 个大类**：风景 / 摄影 / 人物 / 动漫 | `grp:<分类码>:<标题>` |
| 锁定 `qh360` | 360 自家 18 类（按 cid 数值排序） | `local:<cid>` |
| 锁定 `wallpapercave` | 23 个检索词 | `local:<检索词>` |
| 锁定 `github` | 23 个目录关键词 | `local:<关键词>` |
| 锁定 `wallhaven` | 通用 23 频道 | `local:<频道 key>` |
| 任意状态（需解锁） | 收藏（固定最前）、NSFW（需 API Key + 密码） | `fav:all` / `nsfw:*` |

**为什么多源时只显示 4 个大类**：各源分类体系差异极大（360 有 18 类、WCV 是检索词、GitHub 是目录名），在混排模式下摆出 23 个子频道，用户点「自然风光」时 360 只能映射到「风景大片」、GitHub 可能匹配不到任何目录 —— 出来的东西自然对不上分类名。**减少选项 = 减少预期落差**。想看精细分类，就锁定单个源。

### 3.3 浏览与使用流程

```
启动 ─┬─ StartMinimized=true ─→ 只驻托盘，不显示窗口
      └─ false ─→ 显示主窗口
                │
                ├─ 选中树节点 ─→ LoadPageAsync() ─→ 并发取多源 ─→ 交错合并 ─→ 瀑布流铺卡片
                │                                      │
                │                                      └─ 卡片进入可视区才加载缩略图（懒加载）
                │
                ├─ 滚动到底部 ─→ OnNearBottom ─→ 自动加载下一页（无限下拉）
                │
                ├─ 点击卡片 ─→ 预览窗（先摆缩略图占位，再加载原图并预缩）
                │
                └─ 确认 ─→ 设为壁纸 / 收藏 / 加入轮换池
```

**无限下拉的边界处理**：取空时不是立刻停止，而是回第 1 页重来（随机排序换新 seed）—— 连续 6 次都无新增才判定频道耗尽，显示「没有更多结果」。已加载过的图片靠 `StoreId` 去重，不会重复出现。

### 4.2 数据流（一次翻页）

```

   │
   ├─ MainForm.AfterSelect → 解析 Tag（fav:/nsfw:/grp:/local:/频道 key）
   │                         写入 _currentChannelKey / _currentLocalChannel
   │
   ├─ MainForm.LoadPageAsync()
   │     ├─ 构造 ChannelDef（local 分支用占位定义，见 §8.2 踩坑）

   │
   ├─ 各源内部：

   │
   ├─ MainForm：BeginBatch → 逐张 AddCard（去重/黑名单过滤）→ EndBatch
   │
   └─ MasonryPanel.Relayout() → 进入可视区的卡片触发 OnCardVisible
          └─ MainForm.LoadThumbAsync() → 缓存命中/网络取图 → 解码缩放 → 写缓存 → 交付
```

## 五、源抽象层

### 5.1 接口契约

```csharp
internal interface IWallpaperSource
{
    string Key { get; }                                   // 唯一标识
    string DisplayName { get; }                           // 菜单显示名
    bool NeedsApiKey { get; }                             // 是否需要 API Key
    bool IsReady(AppConfig cfg);                          // 当前配置下是否可用
    string StatusText(AppConfig cfg);                     // 状态提示文本
    IReadOnlyList<(string Id, string Name)> SupportedChannels(AppConfig cfg);  // 本源自己的分类（v1.5.5）
    Task<IReadOnlyList<WallpaperItem>?> FetchAsync(AppConfig cfg, SourceFetchRequest req, CancellationToken ct);
}
```

**返回值的三态语义**（重要，容易用错）：

| 返回值 | 含义 | 上层行为 |
| --- | --- | --- |
| `null` | 本次**失败**（网络错/解析错） | 记 Warn，跳过该源，不影响其他源 |
| `空列表` | **没有更多**结果（分类无映射、检索无命中） | 记 Info，正常参与合并，不视为错误 |
| `非空列表` | 成功 | 参与 round-robin 合并 |

区分二者是为了让日志可归因：空列表说明「这个源对这个分类本来就没内容」（设计如此），`null` 说明「这个源这次出了问题」。

### 5.2 取数请求

```csharp
internal sealed class SourceFetchRequest
{
    public int Page { get; init; } = 1;
    public int PerPage { get; init; } = 24;
    public string? Seed { get; init; }                    // 随机种子，换一批时变化

    public string WhCategory { get; init; } = "100";      // wallhaven 专用
    public string WhQuery { get; init; } = "";
    public string Purity { get; init; } = "100";
    public string Sorting { get; init; } = "random";

    public string ChannelKey { get; init; } = "";         // 二级频道 key
    public IReadOnlyList<string>? GroupKeys { get; init; } // 一级分类的全部子频道 key（v1.5.4）
    public string LocalChannelId { get; init; } = "";      // 源私有分类 id（v1.5.5）
    public string Keywords { get; init; } = "";            // 通用关键词（Query 去掉 + 号）
}
```

三个分类相关的字段构成**优先级链**，各源按自己的规则解释：

| 字段 | 来源 | 各源如何用 |
| --- | --- | --- |
| `LocalChannelId` | 单源浏览时的 `local:` 节点 | 360 → cid；WCV → 检索词；GitHub → 目录关键词；wallhaven → 频道 key |
| `GroupKeys` | 一级分类 `grp:` 节点 | **在该组内按页轮换取一个**，翻译成自己的分类/检索词 |
| `ChannelKey` | 二级频道节点 | 查映射表 |

`GroupKeys` 的存在理由（v1.5.4 引入）：一级分类本身没有具体 tag。若不给检索线索，360 会退化成「按页轮换自家分类」（点风景出来萌宠动物），GitHub 关键词落空后退回全库（什么都来）—— 这正是「点分类出来很乱」的主因。

### 5.3 各源的分类映射策略

**360**（`Qh360Source`）

- `CidNames`：全部 18 个 cid → 名称，直接作为 `SupportedChannels` 返回（**不是** 旧的 6 项 `Categories` 轮换表）。
- `ChannelCid`：23 个频道 key → 360 cid，**宁缺毋滥**。v1.5.4 删掉了 5 个硬凑的映射：

  | 删除的映射 | 曾映射到 | 实测结果 |
  | --- | --- | --- |
  | `photo_city` | 炫酷时尚(10) | 张冠李戴 |
  | `photo_space` | 风景大片(9) | 张冠李戴 |
  | `photo_minimalism` | 小清新(15) | **返回水稻 / 芯片特写** |
  | `people_street` | 炫酷时尚(10) | 张冠李戴 |
  | `people_art` | 爱情美图(30) | 张冠李戴 |

- **映射不上就不出图**（返回空列表），不再按页轮换自家分类。日志会记 `qh360: 频道 X 在 360 无分类映射，本页不出图`。

**WallpaperCave**（`WallpaperCaveSource`）

- `ChannelTerm`：23 个频道 key → **单个**检索词。实测双词组合（如 `"city architecture"`、`"cars vehicles"`）大量返回 0，故逐频道只给一个词。
- 专辑过滤：slug 或标题含 `phone` / `mobile` / `vertical` / `tablet` / `iphone` / `android` / `watch` / `square` / `tall` 的专辑**整张跳过**；专辑内的图片再按 `width > height` 逐张过滤。
- 翻页策略：每页取「一个专辑」（按页在专辑列表中轮换），同一专辑内按页切片继续深入。

**GitHub**（`GitHubWallsSource`）

- `ChannelMap`：23 个频道 key → 目录关键词**数组**。v1.5.4 删掉 `vaporwave`（合成波美学≠风景）、`relaxing`（内容不确定）、`surreal`（与「极简」不符）。
- 匹配逻辑：取关键词**并集**与文件目录名做包含匹配；命中则只出该目录的图，**落空则不出图**（v1.5.4 取消「退回全库」兜底）。
- 图片过滤：扩展名限 `.jpg/.jpeg/.png`，**blob ≤ 1MB**（`MaxBlobBytes`）。若整批被滤空则自动放宽到全量，保证分类不空。
- 小图优化：文件名形如 `wallhaven-<id>.jpg` 时，把缩略图改写成 `https://th.wallhaven.cc/small/<id 前两位>/<id>.jpg`（约 27KB），原图作为 `ThumbFallback`。实测对比 GitHub 原图 6.3MB / 3.0s，**流量降到 1/230**。

**wallhaven**（`WallhavenSource`）

- 本应用的频道体系本体，`SupportedChannels` 就返回 `Channels.All` 的 23 项。
- 单源浏览时，`LocalChannelId` 即频道 key，就地查出 `Category` / `Query` 交给 `WallhavenClient`。

## 六、取数链路设计

### 6.1 两条链路

应用有两条独立的取数链路，服务于不同目标：

| 链路 | 实现 | 服务对象 | 层级 |
| --- | --- | --- | --- |
| **源通用链路** | `SourceHttp` + `CdnMirror` | 360 / WCV / GitHub / 非 wallhaven 缩略图 | 直连×镜像候选 → 手填代理×镜像候选 |
| **wallhaven 专用链路** | `WallhavenClient` | wallhaven 全部请求 | 直连 → 反代 → 用户代理（四级粘性） |

### 6.2 源通用链路：镜像候选展开

`CdnMirror.Candidates(url)` 把 GitHub 系 URL 展开成 **5 条等价链路**，按实测耗时排序：

| # | 链路 | 实测耗时 |
| --- | --- | --- |
| 1 | `raw.githubusercontent.com/...` | 0.4s |
| 2 | `ghproxy.net/<raw>` | 1.1s |
| 3 | `cdn.jsdelivr.net/gh/<repo>@<branch>/<enc>` | 2.0s |
| 4 | `fastly.jsdelivr.net/gh/...` | 2.6s |
| 5 | `gh-proxy.com/<raw>` | — |

非 GitHub 系 URL 原样返回单条，调用方无需分支。已被公共反代包过一层的地址会**剥掉外层再解析**（防止无限套娃），识别 `ghproxy.net` / `ghproxy.cc` / `gh-proxy.com` / `ghfast.top` / `gh.llkk.cc` / `hub.gitmirror.com` 等。

`SourceHttp` 的遍历顺序：

```csharp
foreach (var (client, tier) in Tiers(cfg))        // 直连 → 最多 2 条手填代理
    for (var i = 0; i < candidates.Count; i++)    // 镜像候选按序
        if (成功) { Note(...); return; }
```

**关键参数**：

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `TextTry` | 8s | 文本请求单次尝试上限 |
| `BinTry` | 20s | 二进制（图片）单次尝试上限 |
| `ConnectTimeout` | 5s | DNS/TCP/TLS 阶段就快速失败 |
| `MaxProxiesTried` | 2 | 避免 N 代理 × M 候选 组合爆炸 |
| `HttpClient.Timeout` | `InfiniteTimeSpan` | **超时一律由 CTS 精确控制** |
| `MaxConnectionsPerServer` | 6 | |

最后一条是关键教训：v1.5.1 的整页空白，根因就是「`HttpClient` 超时对**挂起的连接**不生效」，一次请求挂着 30~63s 拖死整页。改用每跳独立的 `CTS.CancelAfter` 后，单条链路最坏 8s 就换下一条。

### 6.3 可观测性：不刷屏的链路日志

`Note(tier, url, index, ms)` 只在两种情况记 Info：

1. 走了**非直连**链路（用了代理）；
2. 发生了**镜像降级**（不是第 1 条候选，即 raw 失败了）。

且每个「链路 × 站点」组合**只记一次**（`Reported` 并发字典）。日志形如：

```
source http: raw.githubusercontent.com via 镜像 #2 2280ms
```

直连首选候选成功是常态，不记 —— 否则日志会被淹没。

### 6.4 wallhaven 专用链路

`WallhavenClient.RebuildChain()` 生成的链路顺序（按优先级）：

1. **直连**（`EntryKind.Direct`）—— 仅当 `_directDead == false`；`ConnectTimeout = 3s`，整体 5s。
2. **反代** —— 来自 `cfg.CfProxyUrls`；列表为空时用 `DefaultMirror.Url`，此时 Kind = `DefaultMirror`。
3. **用户代理** —— `cfg.ProxyUrls` 池中的每一条。

**手填代理锁定**（`ManualProxyLocked`）是特例：链路只生成这一条，不优选、不降级、失败即失败。

#### 6.4.1 内置默认反代

`Core/DefaultMirror.cs` 存储内置反代地址，**混淆保存、绝不明文输出**：

```csharp
// 每条：(Part1, Part2)，拼接后构成完整 Base64
private static readonly (string A, string B)[] Parts =
{
    ("KT11KDU/MHU1Pi06Mz",          "c3Oix0dGEoKy8vMw=="),   // 主
    ("KT11KDU/MHU1Pi06Mzc3Oix1aS",  "x0dGEoKy8vMw=="),       // 备
};
public static IReadOnlyList<string> Urls { get; } = Parts.Select(p => Decode(p.A, p.B)).ToList();
```

编码方案：明文 → UTF8 → 每字节 XOR `0x5B` → 逆序 → Base64，再按固定位置切成两段分别存放。

**多地址设计**（v1.5.6 起）：同一个 Worker 部署在多个域名上，全部入链。用户未填反代时
`_mirrorRaw = DefaultMirror.Urls`，于是链路变成「直连 → 主反代 → 备反代 → 用户代理」。
主地址被墙/被限流时自动滑到备用，不必等用户自己配代理。

链路标识带序号（`mirror:default:0` / `mirror:default:1`），确保主备能被分别记忆；
配置里若残留旧格式 `mirror:default`（无序号），按「主地址」兼容处理。

**设计约束（代码注释中明确要求，必须遵守）**：任何日志、状态栏、托盘提示、设置界面都**不得显示该地址**。原因：反代是公共资源，地址一旦公开就会被爬虫抓取并滥用，最终导致被封，损害所有用户。因此：

- `ActiveProxyAddress` 在 `DefaultMirror` 时返回空串；
- `ActiveProxyName` / `ActiveTier` 统一显示为「默认代理」（多条时加「（备N）」后缀，只报序号不报地址）；
- `PreferredChain` 持久化时只写 `mirror:default:<序号>`，**不落地址**；
- `RebuildChain()` 的日志只报数量（`mirror 2(默认)`），不打印内容。

#### 6.4.2 链路粘性记忆（`PreferredChain`）

用户要求「当前代理有效时默认用它，连不上才开始轮换」。实现为字符串标识 + 启动时指针复位：

| 值 | 含义 |
| --- | --- |
| `direct` | 直连有效 |
| `mirror:default` | 内置默认反代有效（不落地址） |
| `mirror:<用户自填反代>` | 用户反代有效 |
| `proxy:<地址>` | 用户代理有效 |

- `ApplyPreferredChain()` 把 `_chainIdx` 移到匹配该标识的层级；
- `MeasureActiveLatencyAsync()` **先调 `ApplyPreferredChain()` 再测速**（v1.5.5 修复）；
- 测速成功（`RememberChain()`）即持久化 —— 「这条链路有效」是实测结论，不是猜测。

#### 6.4.3 并发链路横跳修复（v1.5.5 核心）

**问题**：多个并发请求共享一个 `_chainIdx`，各自无条件推进：

```
请求 A 失败 → failover -> 默认代理   （_chainIdx = 1）
请求 B 失败 → failover -> 直连       （_chainIdx = 0）← 把 A 刚切好的又切回去
```

结果 wallhaven 永远用不对链路（重试总是用回被墙的直连），用户观感就是「默认反代怎么都无法访问」。

**修复**：`RotateProxy(used)` 只在自己失败的那条**仍是当前链路**时才推进：

```csharp
private void RotateProxy(in (EntryKind Kind, string Url, string? User, string? Pass) used)
{
    var cur = Current();
    if (cur.Kind != used.Kind || !string.Equals(cur.Url, used.Url, StringComparison.OrdinalIgnoreCase))
        return;   // 别人已经切换过了：我的重试直接用新链路即可，不要再推进（否则互相踩）
    ...
}
```

#### 6.4.4 直连快速失败

国内直连 wallhaven 必然超时，因此：

- `_directDead` 标志：直连失败一次后，**本会话不再放进链路**，避免每次重建后首个请求都先白等；
- 直连整体超时 **8s**（`ConnectTimeout` 3s），远低于其他链路的 30s；
- 反代链路用直连客户端（反代本身境内可达，不应再套代理）。

## 七、多源聚合

### 7.1 源集合的确定（`SourceRegistry.Enabled`）

```csharp
public IReadOnlyList<IWallpaperSource> Enabled(AppConfig cfg)
{
    // v1.5.5：锁定「浏览源」时硬保证只取它 —— 不再有任何"兜底加回默认组合"
    if (!string.IsNullOrWhiteSpace(cfg.BrowseSource))
    {
        var only = Find(cfg.BrowseSource);
        if (only != null && only.IsReady(cfg)) return new[] { only };
        Logger.Warn($"browse source '{cfg.BrowseSource}' 不可用，回退到多源混排");
    }

    var keys = cfg.EnabledSources;
    if (keys == null || keys.Count == 0) keys = DefaultEnabled.ToList();
    var list = keys.Select(Find).Where(s => s != null && s.IsReady(cfg)).ToList();
    if (list.Count == 0) /* 退回默认组合 */ ;
    return list;
}
```

这是「筛选单个源还会混入其他源」的**根治点**：`BrowseSource` 分支直接 `return`，后面所有兜底逻辑都不会执行。

### 7.2 并发聚合与交错

```csharp
var per = Math.Max(6, req.PerPage / sources.Count);   // 每源取这么多
```

每个源：复制一份请求（改 `PerPage`），独立 `CancellationTokenSource` + `CancelAfter(PerSourceTimeout)`。

**单源超时 = 25s**（v1.5.5 从 12s 放宽）。理由（代码注释原文）：

> 12s 太紧：wallhaven 的链路是「直连 → 反代」，直连超时（5s）+ 限流间隔（1.5s）+ 重试延迟（2s）已经逼近 12s，导致它**永远没机会走反代**就被外层砍掉（日志特征：`failover -> 默认代理` 与 `source timeout after 12s` 同时出现）。

合并：**round-robin 交错**，避免「前一半全是 A 源」：

```csharp
for (var idx = 0; idx < maxLen; idx++)
    for (var s = 0; s < results.Length; s++)
        if (results[s] != null && idx < results[s].Count) merged.Add(results[s][idx]);
```

全部源失败（`ok == 0`）才返回空列表。日志：`sources merged: 3/3 ok (qh360,wallpapercave,github) -> 24 items`。

### 7.3 配置迁移

`SourceRegistry.NormalizeEnabled(cfg)` 在启动时执行一次：

1. 剔除已不存在的源 key（如 v1.5.0 移除的 bing/picsum/unsplash/pexels/pixabay）；
2. 若发现「有已移除的源」→ 判定为升级用户 → **自动补上新默认源**（避免升级后可用源变少）；
3. 过滤后为空 → 回落默认组合；
4. 有变更才落盘，并记日志 `sources migrated: [...] -> [...]`。

## 八、UI 与渲染

### 8.1 瀑布流面板（`MasonryPanel`）

| 特性 | 实现 |
| --- | --- |
| 自适应列数 | `Math.Clamp(avail / 240, 2, 6)`，理想列宽 240px |
| 真瀑布流 | 每张按图片宽高比算列高，放入**当前最矮的列** |
| 懒加载 | 卡片进入可视区（向下多预备半屏）才触发 `OnCardVisible` |
| 无限下拉 | 距底部 60px 内触发 `OnNearBottom` |
| 内存上限 | `MaxCards = 240`，超出后从最早加入的开始释放（含缩略图） |

**v1.5.5 批量重排**：`BeginBatch()` / `EndBatch()`。此前每张卡 `AddCard` 都触发一次 `Relayout()`，加载一页 24 张就是 **O(n²)** 次布局。现在批量期间只在 `_batchPending` 打标记，`EndBatch` 时**统一重排一次**。

### 8.2 缩略图管线

**两级并发闸门**（v1.5.4 从「单一闸门 3」拆分）：

| 闸门 | 并发 | 包裹范围 | 理由 |
| --- | --- | --- | --- |
| `_thumbNet` | 6 | 网络取字节 | 网络等待 IO 密集，可以宽松 |
| `_thumbCpu` | 2 | 解码 + 缩放 | 解码是 CPU/内存密集，必须收紧 |

原设计用一个 3 并发闸门同时管网络和解码，把首屏 24 张串成 8 批。拆分后实测 12 张缩略图就绪 **4.9s → 3.7s**。

**取图路径**（`LoadThumbAsync`）：

```
缓存命中？──是─→ 读缓存（_thumbCpu）──→ 交付
   │否
   ├─ _thumbNet：FetchThumbBytesAsync(item.Thumb)
   │      ├─ URL 含 "wallhaven" → RewriteThumbAlways（强制走反代，不依赖链路状态）
   │      └─ 否则 → SourceHttp.GetBytesAsync（多跳链路）
   ├─ 失败且 item.ThumbFallback 非空 → _thumbNet 再取一次备用地址
   ├─ _thumbCpu：DecodeScaled → TryWriteThumbCache（原子写：.tmp → rename）
   └─ BeginInvoke 交付给卡片（由卡片负责释放旧图）
```

**为什么 `RewriteThumbAlways` 必须强制走反代**：GitHub 图库里有大量 wallhaven 的图，缩略图指向 `th.wallhaven.cc`。若依赖「当前链路是否在反代」来判断，当链路停在直连时就会去直连被墙的域名，挂满 15s 超时。强制改写则稳定。

**缓存自愈**：`TryReadCachedThumb` 发现缓存文件是旧版留下的**原图**（宽 > `ThumbRawThreshold`）时，就地重新编码成 240px 小图覆写缓存 —— 浏览一遍即可把历史大图缓存全部换掉。

### 8.3 两段缩放（`ScaleTo`）

```csharp
private static Bitmap ScaleTo(Image src, int width)
{
    if (src.Width > width * 2)
    {
        // 第一段：Bilinear 粗缩到 2× 目标宽（HighSpeed 偏移模式）
        var mid = new Bitmap(width * 2, ...);
        ... DrawImage(src, 0, 0, midW, midH);
        return ScaleTo(mid, width);          // 递归
    }
    // 第二段：源已只有 2× 目标宽 → Bicubic 精缩很快
    ... InterpolationMode = HighQualityBicubic;
}
```

**理由**：直接拿 `HighQualityBicubic` 把 5120×2880 缩到 240px 是纯 CPU 灾难 —— 每个输出像素要采样输入的一大片区域。两段法先粗缩到 480px（Bilinear 快），再精缩到 240px，质量几乎无损、耗时降一个数量级。

`PreviewForm.ScaleDown` 用同一套两段逻辑。

### 8.4 预览窗（`PreviewForm`）

v1.5.5 两处改动：

1. **先摆占位**：`ShowThumbPlaceholder(item)` —— 点击卡片后立刻把已有缩略图铺上去，不必干等几 MB 原图下完；
2. **预缩再交给 PictureBox**：

```csharp
var targetW = Math.Max(640, ClientSize.Width * 2);      // ×2 兼顾高分屏
var img = decoded.Width > targetW ? ScaleDown(decoded, targetW) : new Bitmap(decoded);
_pic.Image = img;
```

**为什么必须预缩**：`PictureBox.SizeMode = Zoom` 会在**每次重绘**时把整张图重新插值一遍。5120×2880 的原图，窗口每次重绘（拖动、遮挡恢复、切换）都跑一遍大图缩放 —— 这正是「点一下图 CPU 就飙满」的直接原因。预缩到窗口所需尺寸后，重绘只是贴一张位图。

### 8.5 后端内存与托盘

- 最小化到托盘时 `ReleaseCardsForBackground()`：清空全部卡片与缩略图，让后台常驻内存回到基线（此前只 Hide 窗口，缩略图仍全部常驻）；
- 窗口恢复（`WindowState.Normal && Visible`）时重新 `Reload()`；
- 最小化同时结束 NSFW 会话（`LeaveNsfwSession()`）：切回普通频道 + 锁回密码门禁 + 移除树节点。

### 8.6 设置窗贴主窗

```csharp
public void ShowAttachedTo(Form owner)
{
    var b = owner.WindowState == FormWindowState.Normal ? owner.Bounds : owner.RestoreBounds;
    if (!owner.Visible || b.Width <= 0 || b.Height <= 0)
        b = Screen.FromControl(owner).WorkingArea;

    StartPosition = FormStartPosition.Manual;   // 位置每次显式计算
    Location = new Point(b.Left + Math.Max(0, (b.Width - Width) / 2),

}
```

必须用 `Manual` + 显式计算：`CenterParent` **只在首次 Show 时生效**，之后设置窗会停在上次的位置（用户反馈的「弹出框乱跑」）。

## 十、关键踩坑记录

以下问题都曾真实发生并已修复，记录以免重走：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 整页永久「加载中…」 | `_currentChannelKey == "local"` 时 `Channels.Find("local") == null` → `LoadPageAsync` 直接 `return` | 补 `local` 分支的占位 `ChannelDef("local","源分类","100","")` |
| 2 | 点分类出来很乱 | 一级分类无检索线索 → 360 按页轮换自家分类、GitHub 退回全库 | 引入 `GroupKeys`，各源在组内轮换取映射；取消 GitHub 退回全库兜底 |
| 3 | 「反代怎么都无法访问」（表象 1） | 并发请求共享 `_chainIdx` 各自推进 → 链路横跳 | `RotateProxy` 只在链路仍停在自己失败那条时才推进 |
| 4 | 「反代怎么都无法访问」（表象 2） | 单源超时 12s 太紧，wallhaven 没机会走反代就被砍 | 放到 25s；直连超时收紧到 5s（Connect 3s）+ `_directDead` |
| 5 | 设置页状态栏总显示「不可用」 | 测速探针打的是直连（被墙） | `MeasureActiveLatencyAsync` 先 `ApplyPreferredChain()` |
| 6 | 浏览吃流量大 | 缩略图存的是原图（中位 2.33MB、最大 44MB） | 两段缩放存 240px 小图；旧大图缓存读到时就地重编码自愈 |
| 7 | 服务端缩放 CDN 不可达 | `wsrv.nl` / `images.weserv.nl` 本机 URLError | 放弃服务端方案，改本地缩放 |

## 十一、已知限制

1. **本机 WIC 无 WebP 解码器** —— Win11 LTSC 2024 (26100) 上 WPF `BitmapDecoder` 抛 `NotSupportedException`，GDI+ 同样失败，注册表无 WebP codec。因此零依赖路线只能吃 JPEG/PNG，Wallhalla 这类只给 webp 变体的站点无法接入。轻量备选（`Imazen.WebP` / `LibSkiaSharp`）按「轻量化」原则当前不引入。
2. **GitHub API 限流** —— 未认证只有 60 次/小时，故清单必须缓存 24h；触及限流时该源当页不出图（日志提示「稍后自动重试」），不影响其他源。
3. **360 接口是 HTTP** —— 该站不支持 HTTPS，保持原样调用。
4. **反代冗余有限** —— 内置默认反代有主 + 备两条，主失效会自动降级到备；但两条都挂在同一个服务上，同时被封时 wallhaven 只能靠用户自备代理。实测（2026-09-24）两条均 3/3 可用（API 0.8~0.9s / 缩略图 0.7s / 原图 2.3~2.9s），主备降级已在 hosts 屏蔽实验下验证生效。
5. **测试脚本会改用户配置** —— `_verify/` 下的多轮 A/B 脚本曾改动 `EnabledSources`，结束时需恢复三源默认值。
6. **首次冷启动仍有一次直连尝试** —— `PreferredChain` 为空（全新安装）时链路指针在 `direct`，需一次 5s 快速失败才切反代。之后粘性记忆生效。

## 十三、后续可选方向

按优先级排列，均**未实施**：

1. **反代健康度自动排序** —— 目前内置多条反代按固定顺序入链，可改为按实测延迟排序或记录失败次数后动态调整优先级。
2. **WebP 支持** —— 引入 `LibSkiaSharp` 或 `Imazen.WebP`，可解锁 Wallhalla 等只给 webp 的站点。代价是体积增加（与「轻量化」原则冲突，需权衡）。
3. **缩略图解码下沉** —— 目前解码在主线程池；若首屏仍有卡顿，可考虑独立低优先级线程。
4. **源健康度面板** —— 记录每个源的成功率/平均耗时，供用户判断是否值得勾选。

## 附录 B · 术语表

| 术语 | 含义 |
| --- | --- |
| **浏览源**（BrowseSource） | 单选，锁定只看哪一个源；空 = 多源混排 |
| **参与源**（EnabledSources） | 多选，「全部」模式下参与混排取图的源集合 |
| **源私有分类**（LocalChannelId） | 锁定单源时显示的该源自己的分类 id，语义由源自己解释 |
| **一级分类**（GroupKeys） | 风景/摄影/人物/动漫，携带该组全部子频道 key 供各源翻译 |
| **镜像候选**（CdnMirror） | GitHub 系 URL 展开出的 5 条等价链路（raw / ghproxy / jsDelivr ×2 / gh-proxy） |
| **默认代理**（DefaultMirror） | 内置反代，主 + 备多条；地址混淆存储、永不显示 |
| **链路粘性**（PreferredChain） | 记住上次验证有效的链路，启动直接用 |
| **两段缩放** | Bilinear 粗缩到 2× 目标 → Bicubic 精缩，避免大图直接 Bicubic 的 CPU 灾难 |
| **缩略图闸门** | `_thumbNet`(6) 管网络 / `_thumbCpu`(2) 管解码 |
| **StoreId** | 落盘键，wallhaven 用裸 id，其他源带前缀 |
